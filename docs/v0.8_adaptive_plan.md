# Version 0.8 plan: adaptive AI (DRAFT — not approved, and no reserved data has been opened)

Written on 2026-09-24, immediately after Version 0.7 was recorded and **before DRIAMS-C has been downloaded,
extracted or looked at**. It is a draft: the sections marked **DECISION NEEDED** are choices the project
specification does not determine, and they need the project owner's approval before any of the reserved data
is opened. Nothing here may be finalised after seeing a reserved-data result.

Status of the reserved data at the time of writing: DRIAMS-C is not downloaded, not extracted, absent from
every split, and contributes 0 rows to the built dataset. `config.yaml` → `reservation.driams_c` holds the
partition, and a test refuses any configuration that spends it.

## Goal

The specification asks for a simple adaptive / retraining system:

> New hospital data arrives → the existing model evaluates it → performance drift is detected → the model
> can be retrained or fine-tuned using approved new labelled samples → the new model is evaluated → old and
> new model performance are compared.

and, under *Dataset Splitting Strategy*, for an **Experiment D: adaptive retraining on a small subset of
target-domain data**, compared against the non-adaptive results. It also asks for data-drift detection,
performance monitoring, confidence monitoring and model versioning, with metadata per model version.

The research question Version 0.8 answers is therefore narrower than "does adaptation work": it is

> **Does fitting on a small amount of labelled data from a new site improve performance at that site,
> compared with the Version 0.7 model that never saw it?**

## What Version 0.7 established that shapes this

Version 0.7 found **no demonstrated generalisation gap** at any site, with intervals 0.13–0.18 wide. That has
a direct and uncomfortable consequence for Version 0.8, which must be stated before any adaptation is run:

- **If there is no measurable gap to close, an adaptation experiment has little room to show a benefit.** The
  honest framing is that Version 0.8 tests whether adaptation helps *at a site where no loss was
  demonstrated*, and a null result would be the expected outcome rather than a failure of the method.
- The one place Version 0.7 did find a shortfall is the **confidence zone in the later year** (NPV 0.893
  [0.844, 0.937] against a 0.95 target), and that result is confounded by recalibration. Recalibrating a
  zone on local labelled data is therefore a more promising adaptation target than chasing AUROC.
- Adding DRIAMS-B (188 rows, 4.7 % of that training part) to the training data showed **no demonstrated
  benefit** at DRIAMS-D. Pooling a small second site is already weak evidence against the naive version of
  "more sites helps".

**DECISION NEEDED 1 — what Version 0.8 should primarily target.** The options are not equivalent:

| Option | Primary outcome | Why it might be the right choice |
|---|---|---|
| (a) AUROC at the new site | ranking quality | matches the specification's wording most literally |
| (b) Calibration and the confidence zone | Brier, NPV at the fitted edge, coverage | the only place Version 0.7 found a real shortfall; clinically the most meaningful |
| (c) Both, with (b) as primary | – | more work, but avoids reporting only the metric with no headroom |

I recommend **(c) with calibration primary**, because Version 0.7 leaves essentially no headroom in AUROC and
real headroom in the zone. This must be fixed before the data is opened, or the choice becomes a result.

## The reserved data, exactly

Fixed in the Version 0.7 plan's 2026-09-24 addendum and in `config.yaml`, before C's contents were seen:

| Archive | `DRIAMS_C.tar.gz`, 12.43 GB, SHA-256 `77c8097e…85b7867` (verified against Dryad's record) |

| Grouping | whole patient groups where C has a patient identifier, otherwise whole spectra |

**Before C may be used at all**, in this order:

1. Download (browser; Dryad refuses scripted downloads) and register with
   `scripts/download_driams.py --site C --from-file …`, which verifies the SHA-256.
2. Extract `id`, `binned_6000` and the E. coli `raw` spectra.
3. **Check the pre-registered pair-selection rule on C**, as protocol section 3 requires: *E. coli* ×
   ciprofloxacin must have enough resistant and susceptible samples under the same rule used for A. If it
   does not, C is reported unusable **with its counts**, and the fallback applies.
4. Build C as a **separate cohort** with the same preprocessing settings, so it shares the
   `feature_fingerprint` and has its own `row_fingerprint`. The primary dataset, its splits, the saved models
   and every logged result stay untouched (protocol amendment 3, point 4).
5. Only then may the 70/30 partition be drawn — and it is drawn from the *whole* C cohort with seed 42,
   before any label is inspected.

## Proposed boundaries

| Part | Rows | May be used for | May not be used for |
|---|---|---|---|
| A (+B) training, as in Version 0.7 | existing | the starting model | – |
| C adaptation, 70 % | to be determined | fitting or fine-tuning; choosing how much data to use; choosing the adaptation method; recalibrating; refitting the confidence zone | reporting a headline result |
| C held-out, 30 % | to be determined | **one** scoring per final model | anything that influences a model, a threshold, a zone or the method |

**Leakage protections**, to be enforced in code and not only documented:

- The C partition keeps **whole patient groups** together where C has identifiers; where it does not, each
  spectrum is its own group and the intervals are sample-level with unknown within-patient dependence
  (amendment 1, point 2).
- The held-out 30 % is added to `evaluation.locked_test_splits` (or an equivalent guard) **until** the
  Version 0.8 run, so every script refuses it, exactly as `temporal` and `external` were refused until
  Version 0.7.
- A start-up assertion that the adaptation and held-out parts share **0 rows and 0 patient groups**, and that
  neither intersects any Version 0.7 training part.
- The append-only log gains rows only; the run compares it before and after and records its hash.

## Baseline to compare against

The comparison must be against a model that never saw C, otherwise "adaptation helped" is unfalsifiable:

1. **Primary baseline:** the saved Version 0.7-era project model (`v0.4.0-tuned_lightgbm-random-seed42`),
   scored on the C held-out part. It has never seen any C row, so this is clean.
2. **Secondary baseline:** the `external` refit from Version 0.7 (trained on A only), scored on the same
   rows, so the comparison is not confounded by which A rows were used.
3. **Reference row:** prevalence on the C held-out part, as protocol section 5 requires.

Because baselines and the adapted model are scored on the **same** held-out rows, differences use a
**paired** bootstrap (the same resamples for both), as in the Version 0.7 A+B→D comparison.

**DECISION NEEDED 2 — the adaptation method.** The specification says "retrained or fine-tuned" without
choosing. Candidates, from least to most invasive:

- **Recalibration only** — refit the sigmoid and the confidence-zone edge on C's adaptation part, leaving the
  tree model untouched. Cheapest, directly targets the one shortfall Version 0.7 found, and is the most
  realistic thing a laboratory could actually do.
- **Refit on A + C adaptation** — the same fixed setting, more data. Comparable to `external_ab`.
- **Fine-tune** — continue boosting from the saved model on C's adaptation part.

I recommend pre-registering **recalibration only as primary**, with refit-on-A+C as a pre-specified
secondary, and explicitly *not* running a search on C. More options mean more ways to find a favourable one.

**DECISION NEEDED 3 — the learning-curve question.** The specification says "a small subset". If Version 0.8
tries several adaptation-set sizes (say 25 %, 50 %, 100 % of the 70 %), each size is a separate model and
therefore a separate scoring of the held-out part. That is defensible only if every size is pre-registered
and **all** results are reported. Alternatively one size is fixed in advance. The first is more informative;
the second is harder to misuse.

## Metrics

- **Primary:** whichever DECISION NEEDED 1 selects, fixed before opening the data.
- Always reported together: AUROC, PR-AUC next to the resistant share, Brier next to the prevalence Brier,
  calibration slope and intercept, and at the operating threshold sensitivity, specificity, balanced
  accuracy and the full confusion matrix.
- **Confidence zone:** coverage and NPV at the edge, both for the carried-over Version 0.6 edge and for an
  edge refitted on C's adaptation part — reported as two clearly separated numbers, because one tests
  transfer and the other tests local fitting.
- **Drift, without labels:** the Version 0.7 feature-only diagnostic (per-bin standardised mean difference,
  the lowest bins separately, and the same measure on the Version 0.6 regions), plus prediction- and
  confidence-distribution comparisons. The specification asks that data-drift monitoring be **clearly
  distinguished from performance monitoring**, so drift numbers are reported in their own section and never
  described as performance.
- **Model versioning:** metadata per version as the specification lists — training date, training sites,
  dataset size, target organism, target antibiotic, AUROC, F1, PR-AUC — which the existing model-card format
  (`amr-model-bundle/1`) already mostly carries and can be extended to cover.

## Uncertainty estimation

Unchanged from the approved protocol: 2,000 bootstrap resamples of whole patient groups, 95 % percentile
intervals, seed 42; paired bootstrap for models scored on the same rows; the second-level unpaired interval
only where test sets share no rows. Five seeds (42–46) for anything with random training, reporting mean and
range plus intervals for seed 42.

## Success and failure criteria, to be fixed before opening the data

The point of writing these now is that they cannot be chosen afterwards.

- **Adaptation helps** only if the paired 95 % interval of (adapted − baseline) on the primary metric
  **excludes 0** in the favourable direction.
- **Adaptation does not demonstrably help** if that interval includes 0 — reported in exactly those words,
  never as "no difference" and never as "adaptation works".
- **Adaptation hurts** only if the interval excludes 0 in the unfavourable direction.
- For the confidence zone: the local edge **reaches its target** only if its NPV is ≥ 0.95 or its interval
  covers 0.95 at ≥ 5 % coverage, using the Version 0.6 rule unchanged, with the number of covered spectra
  reported next to it — Version 0.7 showed how misleading a zone number on 51 spectra can be.
- Given Version 0.7's result, a null outcome is a likely and publishable finding. It must be reported with
  the same prominence as a positive one, and the plan says so in advance.

## Reproducibility requirements

Same standard as Versions 0.6 and 0.7, which both met it:

- The plan and any protocol amendment are committed **before** the implementation exists, so the commit order
  itself evidences the pre-registration.
- Every run records dataset name, both fingerprints, split, git commit, full config, seeds and library
  versions; the run must execute from a clean working tree so no `-dirty` hash is recorded.
- Every number in the report comes from a generator script; no metric is typed by hand.
- The run is rehearsed against a scratch log before the permanent one is touched, and the reported files must
  come out identical between rehearsal and production apart from paths, commit and wall-clock timings.
- A start-up gate proves the starting model is reproducible before anything is scored, as Version 0.7's
  faithfulness gate did (it reproduced bitwise).

## What must be pre-registered before the reserved data is opened

A checklist, all of which must be committed first:

1. The three **DECISION NEEDED** answers above.
2. The primary metric and the exact success/failure rule.
3. The adaptation method(s), and how many adaptation-set sizes will be tried.
4. The baselines and which comparisons are paired.
5. The C partition procedure (already fixed: 70/30, seed 42, whole groups) and the leakage assertions.
6. How a C that fails the pair-selection rule is reported, and the fallback.
7. A protocol amendment (number 4) covering: the new cohort, the locked held-out part, and that a
   locally-refitted confidence zone is a *different* object from the carried-over one and must never be
   compared as though they were the same.

## How Version 0.8 avoids changing its methodology after seeing the reserved results

The mechanisms are the ones that have already caught real problems in this project, not new promises:

- **The plan is committed before the code exists.** Versions 0.6 and 0.7 both did this, and the commit dates
  are checkable. A later change is visible as a later commit.
- **The held-out part is locked in configuration** until the run, and every script refuses a locked part
  before computing anything — the guard that Version 0.7's tests exercise deliberately.
- **The log is append-only and hashed.** A second scoring cannot quietly replace a first; it appends, and
  both must be reported. Version 0.7's run compared the log before and after and recorded its hash.
- **The success rule is arithmetic, not judgement.** "Interval excludes 0" leaves nothing to decide once the
  numbers exist.
- **A rehearsal against a scratch log** runs the production code path on the real data without touching the
  permanent record, so defects surface before the irreversible step. This found three real defects before
  Version 0.7's production run.
- **An independent audit pass** after the results exist, checking every written claim against the generated
  files. In Version 0.6 this overturned a headline number; in Version 0.7 it tightened the confidence-zone
  wording.

## What this plan does *not* decide

- Whether DRIAMS-C is usable for E. coli × ciprofloxacin at all. Unknown until it is downloaded and the
  pre-registered rule is checked; the counts will be reported either way.
- The size of the 70/30 parts in rows, for the same reason.
- The three DECISION NEEDED items.
- Whether the specification's "model_v1 / model_v2 / model_v3" versioning should be a registry file or simply
  the existing bundle cards; that is an engineering choice with no bearing on the science, and can be settled
  during implementation.
