## Goal

Three deliverables the specification owes at Version 1.0:

1. **A result page that consumes the API** — the only concrete statement the repository makes about V1.0.
2. **The complete README**: architecture, training, results, limitations, ethics.
3. **Deployment**, which the specification places after local verification.

## The three scope decisions, and why

Settled before planning rather than during implementation.

**The page is served by FastAPI, not a separate frontend.** A single page on the existing app cannot drift
from the API because it is the same process, needs no Node toolchain or build step, and adds nothing to CI.
A separate frontend app would be a second dependency tree and a build to maintain — a large addition to a
research prototype whose own rule 14 prefers the simpler justified option.

**Deployment is documented, not performed.** The service has no authentication by design, and the README
already says it must not be exposed to a network. Writing an honest deployment section — how to run it
locally, why it binds `127.0.0.1`, and what would have to be true before it could be exposed — satisfies
"deployment after local verification" without shipping an unauthenticated service or inventing security work
the specification never asked for.

**The README gains the five owed sections; the per-version history stays.** Those per-version sections are
the record of what was pre-registered and what was found, including the null and mixed results. Rewriting
~1,900 lines of them risks quietly softening a recorded finding, which this project treats as a serious
fault. The five sections are added in front and link down for detail.

## The result page

**`GET /` returns one self-contained HTML page.** The page holds the markup, styling and a small amount of
vanilla JavaScript; it `fetch()`es `POST /predict` with the chosen file and renders the response. The server
does no templating: the route returns the page, and every number on screen comes from the API at runtime.

**No new dependency, verified before deciding.** `HTMLResponse` and `FileResponse` are available through
FastAPI already. `jinja2` is present in the environment only transitively (via the notebook stack), so using
a template engine would mean declaring it as a first-class dependency; the page is therefore static markup
plus `fetch`, and `requirements.txt` is unchanged.

### What the page must show

- the resistance probability, the decision threshold, and the prediction (`Resistant` / `Susceptible`);
- the three-way confidence label, in the API's own vocabulary;
- the advice line whenever the label is the uncertain one;
- the `DISCLAIMER` constant, before or alongside the result, never below the fold;
- the model version;
- the measured preprocessing, inference and total times the response already carries;
- the m/z regions when explanations are requested, named by interval only.

All of it read from the API response. **No string that states a result may be written into the page's
markup**, so the page cannot disagree with the model.

### What the page must never do

1. **Never claim a high-confidence resistant result.** The fitted zones have `upper: null`, so that label is
   unreachable; a spectrum at p = 0.945 is still reported `Uncertain`. The page must render that honestly
   rather than styling a high probability as a confident call, and must not imply a confidence the model
   does not have.
2. **Never name, rank or suggest an antibiotic** (CLAUDE.md rule 13).
3. **Never use the words "diagnosis", "confirmed" or "recommended treatment"** about its own output
   (amendment 5's clinical-framing rules apply unchanged to the page).
4. **Never display or transmit anything beyond the chosen file.** No patient field, no free-text note, no
   identifier input — the page offers a file chooser and nothing else.
5. **Never send the file anywhere but this service's own `/predict`.** No third-party script, no CDN, no
   analytics, no font or stylesheet fetched from another origin. Everything the page needs is in the page.
6. **Never persist an upload**, in the browser or on the server.

### What it reuses

The page is a client of the existing contract and adds no serving logic: `POST /predict` for the
prediction, the 0.9.1 error `code` vocabulary for failure messages, `GET /ready` for a "service not ready"
state, and `GET /model-info` for the model description. The upload limits, the suffix allow-list, the
temporary-file discipline and the error mapping are the API's and are not reimplemented.

## The complete README

Five sections added ahead of the version history, each synthesising across versions and linking down.

| Section | Content |
|---|---|
| Architecture | the pipeline from raw spectrum to served prediction, the module map, and where each version's artifacts live |
| Training | the data, the splits and why they are grouped by patient, preprocessing, the search, and calibration |
| Results | the project model's internal and external numbers, the confidence zone, and the adaptation outcome |
| Limitations | the seven per-version limitation lists consolidated, with nothing dropped |
| Ethics | de-identified public data, the research-prototype boundary, why no antibiotic is ever recommended, and what would have to be true before clinical use could even be discussed |

**The honesty rule for these sections, fixed now because this is where the temptation lies.** A summary is
where a project quietly starts sounding better than its record. Therefore:

1. **No claim in a consolidated section may be stronger than its per-version source**, and each headline
   number cites the section it comes from.
2. **Every number is copied from a committed artifact**, never retyped from memory or recomputed
   (CLAUDE.md rules 1 and 3).
3. **The null and mixed results appear in Results, not only in Limitations**: no generalisation gap was
   demonstrated at any site; local recalibration was not demonstrated to help; the A+C refit improved the
   Brier score but lost its confidence zone, so its pre-registered verdict is *mixed*, not success; and no
   arm reached the 0.95 zone target, including both baselines.
4. **The Ethics section makes no claim of clinical validation**, states that the model has no
   high-confidence-resistant answer, and does not present the prototype as closer to use than it is.

## Deployment

A documented section, not an artifact. It must state: how to run the service locally; that it binds
`127.0.0.1` and has no authentication, rate limiting or TLS; that it is single-process and its concurrency
is unmeasured; that uploads are bounded but the service is not hardened against a determined attacker; and
the specific things that would have to exist before exposure could be considered. It must **not** present a
deployment as available, and no container, orchestration or hosting configuration is added.

## Privacy and security, unchanged

Every guarantee from amendment 5 continues to hold, and the page introduces no new surface for breaking
them: no identifier is displayed, logged or transmitted; the uploaded filename is still discarded after its
suffix is read; nothing is persisted; and no response or page may contain a fingerprint, an absolute path,
an archive checksum or a non-finite float. The page is same-origin only, which is also what keeps a
spectrum from reaching a third party.

## What Version 1.0 does not do

No authentication, rate limiting, TLS, multi-worker serving, container, orchestration or public hosting. No
database, no persistence, no user accounts, no model upload, no retraining endpoint, no batch UI. No new
species or antibiotic, no refitting, no new dataset, no change to any model, threshold, zone, metric or
recorded result. The append-only log gains no row and `models/` keeps its audited digests.

# Addendum — 2026-09-28: three obligations the plan above left unstated

Written before any page code, and **appended**: nothing above this line is altered, and the section above is
verified byte-identical to its state at commit `d1718cc`. Recorded as
[protocol amendment 7](evaluation_protocol.md#amendments).

Implementation review of the plan above against the implementation directive found three gaps. None of them
relaxes a requirement; two add one and the third resolves an internal tension.

**Accessibility was absent.** The plan specifies what the page must show and must never claim, but says
nothing about whether a reader can perceive it. Amendment 7 fixes the requirements: a labelled file input, a
keyboard-operable submit, an `aria-live` status region, semantic landmarks, **confidence conveyed as text and
not by colour alone**, and focus moved to the status region after a render. These become acceptance criteria
alongside the ten already locked.

**The disclaimer's single source of truth.** Verification item 3 requires a test that asserts the page
carries `DISCLAIMER` *by importing the constant*. Pasting the text into the HTML would satisfy the test today
and drift the moment the constant changed. The page therefore holds named placeholders and the route
substitutes the canonical constants when serving — a fixed allow-list of project constants, never anything
from a request.

**Item 6 is scoped to the result region.** Item 6 forbids hard-coded result strings; item 7 requires
explaining that a high-confidence-resistant answer is unreachable, which means naming it. The result region
is empty in the served markup and filled only from a response; explanatory copy lives elsewhere. A label in
an explanation is not a hard-coded result.

One boundary is recorded rather than fixed: the suite does not execute the page's JavaScript, because CI
installs Python only. The page is instead written so the unsafe code cannot exist — no label literal, no
comparison against the returned probability — and the tests assert that structure.
