# Version 0.9 plan: the backend API (fixed before any endpoint was written)

**Date: 2026-09-25.** Recorded as [protocol amendment 5](evaluation_protocol.md#amendments). Written and
committed before any API code existed, on top of Version 0.8 (results commit `849cad7`, merged to `main` as
`ba7cb3e`, log SHA-256 `c395fcb3…76e0c7`, 89 data rows).

This version is engineering, not an experiment. It states no hypothesis, fits nothing and produces no new
metric, so it has no endpoint, no statistic and no success criterion in the scientific sense. What it does
have is a **safety contract**, and that is what this document fixes in advance: the limits the API enforces,
the fields it will never return, the errors it must produce, and the clinical claims it must not make.

## Goal

Expose the existing, frozen serving path over HTTP so that a spectrum can be submitted and a research
prediction returned, without changing anything about the model and without becoming a way to reach protected
data. `src/predict.py::predict_spectrum_file` already performs the whole prediction; this version adds
transport, input validation and an explicit response contract around it, and nothing else.

## Endpoints

1. **`GET /health`** — whether the service can serve. Reports `status` (`ok` / `degraded`), whether the model
   and the confidence zones loaded, the model version, the API version and uptime. Returns 503 when
   `degraded`. It reports no model internals and no paths.
2. **`POST /predict`** — one uploaded raw spectrum file. Returns exactly the fields
   `scripts/predict_spectrum.py` already prints: species, antibiotic, prediction,
   `resistance_probability`, threshold, `model_version`, `preprocessing_ms`, `inference_ms`, `total_ms`,
   confidence, explanation, disclaimer, plus `advice` when the confidence label is `Uncertain`. The API and
   the CLI must agree field for field; a test asserts it.
3. **`POST /batch-predict`** — several uploaded spectra in one multipart request. Results are returned in
   request order, each carrying its index and either a prediction or an error. **One invalid file does not
   fail the batch**, because a partial result is more useful than a blanket rejection and matches how a
   laboratory submits a plate.
4. **`GET /model-info`** — algorithm, hyper-parameters, calibration, target species and antibiotic, label
   map, threshold and the rule that chose it, a description of the training data, the evaluation metrics,
   the external-site results, the confidence-zone description, the measured latency, and the disclaimer.

## Input validation and limits

The limits are set from measurement, not taste. Across 300 raw spectrum files from each of DRIAMS-A, B, C
and D, a real spectrum is **403–467 KB** and about **20,700 points** (a sampled file: 433,310 bytes,
20,748 lines). The caps are therefore roughly **ten times** the largest legitimate input: they exist to
bound abuse, and no genuine spectrum can reach them.

| Limit | Value | Enforced |
|---|---|---|
| File suffix | `.txt` | before the file is opened; the filename is then discarded |
| Bytes per upload | 4,000,000 | **while the body streams**, aborting as soon as the counter passes it |
| Points per spectrum | 200,000 | after reading, beside the existing `min_raw_points = 100` floor |
| Files per batch | 20 | before any file is read |
| Bytes per batch | 32,000,000 | while the bodies stream |

Three rules govern how these are implemented:

1. **No uploaded byte is ever deserialised, imported or executed.** Nothing from a request reaches
   `joblib.load`. A saved bundle can run code when it is loaded, which is why no endpoint accepts a model,
   a configuration or any filesystem path from the client, and why a `.joblib` upload is refused at the
   suffix gate without being opened.
2. **An oversized body is never fully buffered.** The byte counter aborts the stream mid-flight, so a
   refusal costs the limit, not the payload.
3. **The limits are keyword parameters, not configuration fields.** `PreprocessingConfig.fingerprint()`
   hashes every field except `spectrum_folder`, so adding a limit to it would change the feature
   fingerprint `347cbd6d5d956ff9`, and `predict_spectrum_file` refuses a bundle whose stored fingerprint
   does not match. Every new parameter therefore defaults to `None`, meaning today's exact behaviour, and a
   test asserts the fingerprint is still `347cbd6d5d956ff9`.

## What is never served

The API builds every response from an explicit allow-list of declared fields. It never serialises a bundle,
a model card or a saved JSON report by reflection. The following must not appear in any response, and a test
asserts each one's absence:

- `feature_fingerprint` (`347cbd6d5d956ff9`), `dataset.row_fingerprint` / `split.dataset_fingerprint`
  (`151415a4d03dbcc5`), `dataset.x_sha256`;
- `git_commit`, `code_fingerprint`;
- any absolute path, including `paths.driams_root` (`C:/DRIAMS`);
- any DRIAMS archive checksum;
- the Version 0.8 Platt coefficients and partition fingerprints;
- **any patient, case or order number, any DRIAMS spectrum UUID, and any uploaded filename.** Raw DRIAMS
  files are *named* after the spectrum UUID and repeat it in their `#` comment lines, so the filename is
  read for its suffix and then dropped, comment lines are never echoed, and neither is written to the log.
  This extends the `UUID_LIKE` scan of `tests/test_privacy.py` to the serving path.

**No response may contain a non-finite float.** The committed `uncertainty.json` holds a bare `NaN`
(`sides.resistant.achieved`), as do `zone_intervals.json`, `run_config.json` and `run_status.json`. Bare
`NaN` is not valid JSON — strict encoders reject it and so does a browser's `JSON.parse`. Any number taken
from a saved report passes through a converter that maps non-finite values to `null`, and a test asserts
every response body survives `json.dumps(..., allow_nan=False)`.

## The confidence label the API cannot return

The Version 0.6 zones were fitted with `"upper": null` and `sides.resistant.exists: false`: the
high-confidence-resistant side could not reach its 0.95 precision target at 5 % coverage (its best was
0.84), so **that zone does not exist**. The API can therefore return only
`"High-confidence susceptible"`, `"Uncertain"`, or `"not available"` when no zone file is loaded. It can
never return `"High-confidence resistant"`. `/model-info` states this explicitly rather than leaving a
consumer to infer it from an absence, and a test asserts both the impossibility and the statement.

## Error contract

Every error returns a message, never a traceback. The mapping is fixed here so it cannot be adjusted to make
a test pass:

| Condition | Status |
|---|---|
| empty, corrupted, non-numeric, too-few-points or otherwise invalid spectrum (`SpectrumFormatError`, `PreprocessingError`) | **422** |
| upload exceeds the byte limit | **413** |
| unsupported file suffix | **415** |
| too many files, or batch byte limit exceeded | **413** |
| model or zones unavailable (`ModelError`) | **503** |
| anything unexpected | **500**, generic message, traceback to the log only |

The body is `{"error": {"type": ..., "message": ...}}`. This mirrors the established script convention —
a plain `Error: <message>` and exit 1 for known failures, exit 2 for unexpected ones — and the existing
exception hierarchy (`DataError`, `SpectrumFormatError`, `PreprocessingError`, `ModelError`, `ConfigError`)
already carries user-readable messages, so they are reused rather than rewritten.

A `ConfigError` at start-up prevents the service from serving at all. A `ModelError` at start-up is recorded
and makes `/health` report `degraded` and `/predict` answer 503: the process neither crash-loops nor
pretends to be healthy.

## Medical-safety contract

1. Every prediction response carries the existing `DISCLAIMER`: an AI research prediction from a research
   prototype, not a clinically validated diagnostic, not a replacement for laboratory antimicrobial
   susceptibility testing, and not a treatment recommendation.
2. A prediction labelled `Uncertain` carries the existing `ADVICE`: conventional antimicrobial
   susceptibility testing is recommended.
3. **No endpoint names, ranks or suggests an antibiotic for a patient.** The API reports a resistance
   probability for the one species–antibiotic pair the model was trained on, and nothing else.
4. `/model-info` reports the **external** results alongside the internal test metrics. Serving only the
   internal AUROC would overstate the model, so the Version 0.7 and Version 0.8 numbers are included,
   including the null and mixed outcomes.
5. No response uses the words "diagnosis", "confirmed" or "recommended treatment" about its own output.

## What this version does not do

No authentication, no rate limiting, no TLS, no multi-worker deployment, no database, no persistence of
uploaded files, no model upload, no retraining endpoint, no format beyond `.txt`, no public hosting, and no
change to any model, threshold, metric or recorded result. The append-only test log gains no row and
`models/` is byte-unchanged. The specification places deployment after local verification, so deployment
belongs to Version 1.0.

# Addendum — 2026-09-26: hardening review

**This section was written after implementation and is marked as such.** The document above is the
pre-registration, committed before any endpoint existed, and nothing in it has been altered. This addendum
records a design review of the shipped service against a fuller engineering checklist, the three defects it
found, and the sections the original document did not cover.

## Defects found and fixed

1. **A degraded `/health` leaked an absolute filesystem path.** The public `detail` field carried
   `str(exc)` from the failed load, which names the file: *"Model file not found: C:\...\best_random.joblib"*.
   The privacy test did not catch it because the forbidden-string list covered `C:/DRIAMS` but not the
   project directory, and a test actively asserted `"not found" in detail`, so the leak was pinned in place
   by a passing test. Fixed: `detail` is now one of two fixed public strings, the real reason goes to the
   log, and a `PATH_LIKE` regex now asserts that **no** response from **any** endpoint, on success or
   failure, contains a drive letter, a UNC prefix or a POSIX system path.
2. **A malformed confidence-zone file was logged and ignored.** `src/predict.py::load_zones`
   deliberately distinguishes an absent file (returns `None`, which is fine) from a file that exists but is
   not a zones record (raises), because *"silently ignoring it would report 'not available' for a model
   that has zones"*. The lifespan performed exactly that silent ignore. Fixed: an unparseable zones file
   now marks the service **not ready**, so `/health` answers 503 and predictions are refused rather than
   quietly downgraded. An **absent** file still serves normally, without a confidence label.
   A follow-up defect surfaced while testing this: `/health` reported degraded while `/predict` still
   answered 200, because the prediction guard checked only for a missing bundle. It now gates on readiness.
3. **`/predict` accepted more than one file.** Two parts under the `file` field returned 200 having
   silently used one of them, so a caller could not know which spectrum was scored. Fixed: exactly one file
   is required, and a violation is 400.

## API scope

Read-only inference over HTTP for one species-antibiotic pair, from the frozen Version 0.4 bundle. No
training, refitting, recalibration, threshold change, zone change, dataset consumption or result mutation.

## Architecture

```
HTTP upload
  -> body-size guard (declared Content-Length, before the body is read)
  -> suffix allow-list (the client's filename is then discarded)
  -> streaming write to a generated temporary name, aborting past the byte limit
  -> src.preprocessing.preprocess_file  (unchanged, with max_points/max_bytes keywords)
  -> src.predict.predict_features       (unchanged)
  -> bundle threshold                   (unchanged)
  -> src.uncertainty.Zones.one          (unchanged)
  -> src.explain, optional              (unchanged)
  -> src.predict.prediction_payload     (shared with the CLI)
  -> declared response model, strict JSON
```

No scientific logic is reimplemented. `prediction_payload` is the single shared output builder, so the CLI
and the API cannot diverge.

## Model lifecycle

`startup -> loading -> ready -> request -> shutdown`. The FastAPI lifespan resolves the configured bundle,
loads it **once**, validates it through `check_bundle`, loads the zones, and records readiness. A missing,
corrupt, non-bundle or digest-mismatched model, or an unparseable zones file, leaves the process running in
a deterministic **not-ready** state: `/health` answers 503 with a fixed public reason and every other
endpoint answers 503. The service never falls back to a different model, never trains, never writes a
result and never downloads anything. Shutdown releases the reference; there is nothing to flush.

## Concurrency assumptions

One uvicorn worker, one process, one loaded bundle, `n_jobs=1` on the pipeline. **The loaded pipeline is
not assumed thread-safe.** Predictions are pure with respect to the fitted object (scikit-learn `predict`
and LightGBM `Booster.predict` do not mutate it), and `n_jobs=1` avoids thread pools per call, so the
conservative position is: correctness first, no shared mutable state introduced, no second model copy and
no worker pool until memory behaviour under load has been measured. Throughput was not a goal and is not
claimed. Determinism is preserved: the same spectrum returns the same probability, asserted by a test that
sends one spectrum three times in a batch.

## Temporary-file policy

Uploads are written to a `TemporaryDirectory` under the operating system temp location, under a
**server-generated** name (`upload.txt`, or `upload_<i>.txt` in a batch). The client's filename is used for
its suffix and then discarded, so path traversal has nothing to traverse - tested with five hostile names
including `../../../etc/passwd.txt` and an absolute Windows path. The directory is removed on the way out
of the context manager, on success and on failure, asserted by tests that patch the module's
`TemporaryDirectory` and check the recorded path no longer exists. Nothing is ever written under the
repository, `data/`, `models/` or `results/`, also asserted.

## Logging policy

Logged: start-up, the served model version, model-load and zones-load failures with their real reason,
readiness transitions. Never logged: spectrum values, uploaded file contents, client filenames, patient or
spectrum identifiers. A test attaches a handler to the `api`, root, `uvicorn` and `uvicorn.access` loggers,
submits a file named after a UUID whose comment lines repeat that UUID, and asserts the UUID appears in
neither the response nor any log record. Unexpected exceptions are logged with their traceback and returned
as a generic 500.

## Performance expectations

Measured, not promised - `scripts/benchmark_api.py`, real uvicorn server over httpx, 200 validation
spectra, durations only:

| | median | p95 |
|---|---|---|
| server startup including model load | 122.11 ms | - |
| cold first request | 88.70 ms | - |
| warm `/predict` round trip | 40.71 ms | 51.81 ms |
| of which preprocessing | 33.20 ms | 43.96 ms |
| of which inference | 1.40 ms | 1.77 ms |
| HTTP overhead | 6.01 ms | - |
| `/predict?explain=true` round trip | 79.49 ms | 89.05 ms |
| batch of 20, per spectrum | 51.34 ms | - |

Three findings worth keeping: the cold first request costs about **2.2x** a warm one; an explanation costs
**+38.78 ms**, roughly doubling a request, which is why it is off by default; and a batch is **not faster
per sample**, because preprocessing dominates by ~24x and the multipart upload costs more than the round
trips it saves. **No service-level objective is declared.** No numerical prediction may be changed in
pursuit of latency.

## Deployment assumptions

Local research use only. Binds `127.0.0.1`; there is no authentication, rate limiting or TLS, so the
service must not be exposed to a network. Single process, no orchestration, no container, no cloud. The
specification places deployment after local verification, so deployment is Version 1.0's concern.

## Backward compatibility with the CLI

`scripts/predict_spectrum.py` is the behavioural reference. Both paths call
`src.predict.predict_spectrum_file` and format with `src.predict.prediction_payload`, so equality holds by
construction rather than by coincidence. A test sends the same spectrum through both against the same
bundle and zones and asserts the key sets match and every field is **exactly** equal except the three
timing fields, which are wall-clock and cannot be.

## Knowingly accepted divergences

These were reviewed and left as they are, so they are recorded rather than hidden:

- **`/health` carries liveness and readiness together** instead of a bare `/health` plus a separate
  `/ready`. A split is the cleaner operational contract and is the right change if this service is ever put
  behind an orchestrator that probes the two differently.
- **The error body's `type` is the internal exception class name** (`SpectrumFormatError`) rather than a
  public code vocabulary (`invalid_spectrum`). The shape is stable and the message is safe, but the
  identifier is an implementation detail that a client should not have to depend on.
- **`/model-info`** rather than `/model`, and it returns more than a minimal card: the training-set
  description, evaluation metrics, external-site results, zone description, limits and measured latency.
  That breadth is deliberate - reporting the internal test figure alone would overstate the model.
- **`/batch-predict` is retained.** It was required by the original Version 0.9 specification, and it is
  built, tested and honestly documented as a convenience rather than a throughput win.
- **The module layout is flat** (`src/api.py`, `src/api_schemas.py`) rather than an `api/` package
  separating app construction, inference service, metadata and errors. `src/api.py` holds routes, handlers,
  upload guards and metadata construction together; splitting it is the first thing to do if it grows.
